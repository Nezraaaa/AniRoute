# Model card — AniRoute road-hazard detector

## Summary

| | Model A — road surface | Model B — obstructions |
| --- | --- | --- |
| Task | Object detection | Object detection |
| Architecture | YOLO11 (Ultralytics), nano or small, chosen in the optimisation series | YOLO11n (Ultralytics) |
| Starting weights | COCO-pretrained | COCO-pretrained |
| Training | **Fine-tuned by us** on public labelled road datasets (transfer learning) | **None** — used as-is |
| Classes | `pothole`, `severe_road_damage` | COCO `person, bicycle, car, motorcycle, bus, truck, dog, horse, sheep, cow` → `road_obstruction` |
| Extra rule | — | Box must stand inside the driving corridor and be ≥ 12% of frame height |
| Weights | `backend/models/aniroute-hazards-v1.pt` | `backend/models/yolo11n.pt` (auto-downloaded) |
| Runtime | PyTorch, ONNX Runtime or OpenVINO on CPU (fastest available is chosen) | same |

Intended use: decision support for drivers of farm-produce vehicles and for mapping road conditions.
Not intended for: autonomous driving, safety-critical braking, or enforcement.

## How YOLO works (plain language)

1. **Backbone** — a convolutional neural network turns the 640×640 image into feature maps: early
   layers respond to edges and textures (crack lines, the rim of a pothole), deeper layers to shapes
   and objects.
2. **Neck** — combines feature maps of several resolutions, so large objects (a bus) and small ones
   (a distant pothole) are both represented.
3. **Head** — for many positions in the image it predicts a box (x, y, width, height), a class
   probability for each class, and is trained so that confident predictions line up with labelled boxes.
4. **Confidence threshold** — boxes below the operating threshold are dropped.
5. **Non-maximum suppression (NMS)** — where several boxes overlap the same object (IoU ≥ 0.5) only the
   most confident one is kept.

YOLO is a **one-stage** detector: one forward pass predicts every box. Two-stage detectors (e.g. Faster
R-CNN) first propose regions and then classify them — often more accurate on tiny objects but slower,
which matters on a laptop CPU or phone. Ultralytics YOLO11 is anchor-free and its nano version (~2.6 M
parameters) runs in tens of milliseconds on a CPU.

## Pretrained vs fine-tuned (transfer learning)

`YOLO("yolo11n.pt")` loads weights learned on COCO (118k everyday photos, 80 classes). We keep what the
backbone and neck already know about edges, textures and shapes; Ultralytics replaces the head with one
for our 2 classes, and training adjusts the whole network to road surfaces. This needs far fewer labelled
images and training time than starting from random weights (preset **E7** in `train.py` trains from
scratch for comparison; it was not run because it needs a GPU).

An optional second model (COCO-pretrained, used as-is, for people, animals and vehicles in the lane) is
implemented but **switched off**: the project focuses on road damage. When enabled, a rule (the driving corridor) decides when such an object is a
hazard rather than normal traffic at the roadside.

## Preprocessing

| Step | Why |
| --- | --- |
| EXIF orientation fix | Phone photos are often stored rotated |
| CLAHE on the LAB lightness channel — **off by default**; optional *auto* (mean lightness < 95 or contrast < 38) or *on* | Meant to brighten night/shadow frames; the validation ablation showed it lowers mAP on our data, so it is opt-in |
| Letterbox to 640×640 | Keeps the aspect ratio (no stretching); grey padding |
| Normalisation to 0–1 | Done inside the YOLO runtime |

Training-time **augmentation** (mosaic, HSV colour jitter, flips, scaling; stronger in E4) is a different
thing: it creates varied training images, while preprocessing is applied to every image at inference.

## Training configuration

Presets are in `ml/train.py`; the submitted results use `E0` (20 epochs) and `E1` (40 epochs) on CPU: image size 640, batch 16, seed 42,
deterministic, early stopping patience 20, Ultralytics default optimiser and learning-rate schedule.

## Thresholds

| Setting | Value | How chosen |
| --- | --- | --- |
| Model A confidence | from `ml/reports/metrics.json → operating_point` (default 0.35 until evaluated) | maximum F1 on the **validation** split |
| Model B confidence | 0.45 | conservative, to avoid alerts for distant objects |
| NMS IoU | 0.5 | Ultralytics default range |
| Driving corridor | horizon at 40% of height, half-width 10% → 25% at the bottom | geometry of a dashboard camera view |
| Alert smoothing | 2 of the last 3 frames, 20 s cooldown, 50 m dedupe | trades a ~1 s delay for far fewer false alerts |

## Limitations and failure modes

- Training data is from India (RDD2022 subset); Philippine roads, lighting and vehicles differ, and there is
  no labelled Philippine test set yet.
- Small or distant potholes and faint cracks are the most common misses (see the size breakdown).
- Wet asphalt, shadows and patched road can look like potholes (false alarms).
- Night, heavy rain and motion blur reduce recall; CLAHE does not fix blur or glare.
- COCO has no carabao, goat, fallen-tree, rock or landslide class; carabaos may or may not be detected
  as `cow`.
- Standing water is not detected automatically.
- Route-risk severity weights (pothole 12, standing water 20, severe damage 25, obstruction 30) are
  heuristics, not validated postharvest-loss coefficients.

## Ethics and privacy

Frames are processed in memory and discarded. Only the frame of a hazard the driver confirms is stored,
with its GPS position; it may show people or plates, so evidence should be stored securely and deleted
after a fixed period in any real deployment. The driver always confirms before anything is saved.
